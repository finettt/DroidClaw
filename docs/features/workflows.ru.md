# Воркфлоу (Workflows)

Воркфлоу позволяют одному запросу в чате разворачиваться в несколько
специализированных субагентов. Воркфлоу — это JSON-файл в рабочем пространстве
по пути `.agent/workflows/<name>.json`. Агент находит воркфлоу через
`list_files(".agent/workflows/")` и запускает их инструментом `run_workflow`;
можно просто попросить агента: «запусти воркфлоу morning-digest».

DroidClaw поставляется с тремя шаблонными воркфлоу. Они копируются в
`.agent/workflows/` при первом запуске, их можно свободно редактировать —
изменённая копия никогда не перезаписывается при обновлении приложения.

## Встроенные шаблоны

| Файл | Что делает |
|------|-----------|
| `morning-digest.json` | Читает события на сегодня через `calendar_list_events`, суммирует их и сохраняет дайджест в `home/notes/morning-digest.md`. Линейная цепочка: `collect → summarize → write_note`. |
| `workspace-audit.json` | Инвентаризирует песочницу через `list_files`/`file_info`, ищет устаревший контент через `search_files` и записывает отчёт в `home/documents/workspace-audit.md`. |
| `two-step-refactor.json` | Агент только для чтения анализирует файл и предлагает ровно одну правку; второй агент применяет её через `edit_file`; необязательный третий перечитывает и проверяет. Демонстрирует `retry` (переопределение `defaults.retry` на уровне узла) и `on_error: continue` (упавшая проверка не убивает запуск). Попросите агента передать путь к файлу и нужную правку в аргументе `input` инструмента `run_workflow`, доступном первому узлу как `{{workflow.input}}`. |

Шаги записи во всех трёх шаблонах явно используют `"approval": "auto_approve"`
с узким набором инструментов. Перед запуском любого узла вы всё равно должны
одобрить внешний вызов `run_workflow` после просмотра содержимого. После этого
эти узлы могут записывать без отдельного запроса для каждого инструмента, даже
если глобальные настройки запрещают инструмент. И `inherit`, и политика
`deny_writes` по умолчанию отклоняют запись внутри воркфлоу: у узлов нет
интерактивного интерфейса одобрения (см. ниже).

Шаблону календаря также нужны включённый календарь в настройках агента и
разрешения устройства на доступ к календарю. См. [интеграцию календаря](calendar.md).

## Формат файла (workflow v1)

Машиночитаемый контракт — `app/src/main/assets/workflow-v1.schema.json`
(JSON Schema draft-07). Верхний уровень:

```json
{
  "version": 1,
  "name": "Читаемое имя",
  "goal": "Одно предложение; подставляется как 'Goal: …' перед каждым промптом узла.",
  "entry": "first_node",
  "output": "{{first_node.output}}",
  "defaults": { "max_turns": 8, "timeout_ms": 180000 },
  "agents": { "first_node": { "prompt": { "text": "…" } } }
}
```

- `version` — обязательно число `1`.
- `goal` *(обязательно)* — добавляется к каждому промпту узла как `Goal: <goal>`.
- `agents` *(обязательно)* — от 1 до 64 узлов. Ключи по шаблону `^[a-z][a-z0-9_]{0,63}$`.
- `entry` — ключ узла или массив ключей. Необязательно; корни выводятся из графа
  зависимостей, но явное указание убирает предупреждение валидатора.
- `output` — шаблон итогового результата, например `{{report.output}}`.
- `defaults` — настройки, применяемые к узлу, если он их не переопределил
  (порядок разрешения: узел → defaults → встроенное значение).

### Поля узла (`agents.<key>`)

| Поле | Значение |
|------|----------|
| `prompt` *(обязательно)* | Ровно одно из `text`, `template` или `from_agent` (плюс необязательный `system`). `from_agent: "x"` подаёт вывод узла x на вход и создаёт ребро зависимости. |
| `model` | Ссылка вида `providerId/modelId`. Если не указана — используется модель по умолчанию из настроек. |
| `depends_on` | Явные рёбра зависимостей. Рёбра также выводятся из ссылок `{{other_node.output}}` и `from_agent`. |
| `inputs` | Именованные шаблонные привязки, доступные узлу как `{{inputs.name}}`. |
| `when` | Условие-guard: `{{node.field}} == 'value'`, `!=` или `contains`, литерал в одинарных кавычках. Ложный guard пропускает узел **и всех его транзитивных потомков**. |
| `allowed_tools` / `denied_tools` | Область инструментов (см. безопасность ниже). `[]` значит «без инструментов» — это не то же самое, что отсутствие поля (= все зарегистрированные инструменты). |
| `approval` | `inherit`, `auto_approve`, `deny_writes`, `strict`. **Отсутствующее значение = `deny_writes`.** |
| `on_error` | `fail` (по умолчанию — прервать запуск), `skip` (пометить упавший узел и всех транзитивных потомков как пропущенные и продолжить), `continue` (записать результат-ошибку и дать потомкам работать с ним). |
| `retry` | `{ "max_attempts": 1–5, "backoff_ms": 0–30000 }`. Повторяются только транспортные ошибки и таймауты, но не ошибки содержимого. |
| `max_turns`, `timeout_ms` | Бюджет ходов и времени. `timeout_ms` — бюджет на весь узел: он покрывает все повторные попытки **и** задержки backoff, а не выдаётся заново на каждую попытку. |
| `output_schema` | JSON Schema структурированного вывода; открывает доступ к `{{node.output.field}}` ниже по графу. |

Шаблоны поддерживают `{{workflow.input}}` (явный аргумент `input` инструмента),
`{{workflow.goal}}`, `{{workflow.name}}`, `{{node.output}}`,
`{{node.output.field}}` (при `output_schema`) и `{{inputs.name}}`. История чата
не копируется в `workflow.input`; без аргумента `input` значение пустое. Пример
аргументов `run_workflow`:

```json
{ "workflow": "two-step-refactor", "input": "Улучши home/example.txt одной небольшой правкой." }
```

### Валидация

Файлы разбираются снисходительно (частые опечатки вроде `propmt` исправляются с
предупреждением), а затем строго валидируются: неизвестные инструменты и ссылки
на модели, несбалансированные `{{ }}`, ссылки на необъявленных агентов и циклы
зависимостей — это ошибки; воркфлоу с ошибками не запускается. Предупреждения
указывают на вероятные ошибки: корневой узел не указан в `entry`, вывод узла
никем не используется и т.п. Размер файла воркфлоу ограничен 64 КБ.

## Модель безопасности

- **Одобрение, привязанное к содержимому.** `run_workflow` всегда требует
  одобрения пользователя, независимо от глобальных настроек авто-одобрения.
  Диалог одобрения показывает разобранный обзор — цель, модели по узлам,
  эффективные списки разрешённых/запрещённых инструментов, эффективную политику
  одобрения — плюс SHA-256 точных байтов файла. При запуске файл перечитывается
  и хешируется заново: если его изменили между просмотром и запуском, запуск
  отклоняется. Хеш, предоставленный моделью, никогда не считается
  доказательством одобрения.
- **Ограниченный реестр инструментов.** Каждый узел видит только свою область:
  `allowed_tools` (или все зарегистрированные инструменты, если поле не задано)
  минус `denied_tools`, причём `run_workflow` исключён всегда — воркфлоу не
  может запускать воркфлоу, рекурсия невозможна.
- **Нижняя граница одобрения.** Политика узла по умолчанию — `deny_writes`:
  инструменты только для чтения работают свободно, а требующие одобрения
  (запись, удаление, изменения календаря) автоматически отклоняются. `inherit`
  тоже использует `deny_writes` внутри воркфлоу: у узлов нет интерактивного
  интерфейса одобрения, поэтому разрешающие глобальные настройки не включают
  запись через `inherit`. `auto_approve` — явное согласие, переопределяющее
  глобальные режимы по инструментам; `strict` отклоняет все вызовы инструментов.
  Инструменты с глобальным `ALWAYS_REJECT` остаются отклонёнными при любой политике, кроме
  явного `auto_approve`. Инструменты, требующие shell, отключены, пока выключен
  доступ к shell.
- **Безопасная загрузка файла.** Имя воркфлоу должно соответствовать
  `[a-zA-Z0-9_-]{1,64}` (без разделителей пути); разрешённый путь не может
  содержать символические ссылки; файлы больше 64 КБ отклоняются.

## Ограничения (честный список)

- **Раннер последовательный.** `max_parallel` принимается схемой, но **не
  реализован**: узлы выполняются по одному в детерминированном топологическом
  порядке, как при `max_parallel` = 1. Сегодня это поле ни на что не влияет.
- `on_error: skip` каскадируется: каждый транзитивный потомок пропущенного узла
  тоже пропускается, а пропущенный узел подставляет пустую строку в шаблоны и в
  `output` воркфлоу.
- Ложный guard `when` ведёт себя как `skip` для узла и его потомков.
- Переопределения модели и одобрения на время запуска очищаются на каждом
  терминальном пути обратного вызова, включая ошибки
  ([#147](https://github.com/finettt/DroidClaw/issues/147)).
- Синхронные ожидания выполняются вне главного looper'а обратных вызовов,
  поэтому воркфлоу не может вызвать ANR приложения через собственные коллбэки
  ([#149](https://github.com/finettt/DroidClaw/issues/149)).
- `timeout_ms` задаёт срок выполнения, а не откат: изменения, уже сделанные
  инструментами, не отменяются.
- Вложенные воркфлоу отклоняются намеренно — это не баг.

## Как написать свой

1. Скопируйте шаблон в `.agent/workflows/` под новым именем по шаблону
   `[a-zA-Z0-9_-]{1,64}.json` — агент может сделать это сам через `write_file`.
2. Держите инструменты записи в минимальном числе узлов. Для узлов, которым
   нужна запись, явно задайте `"approval": "auto_approve"` и узкий список
   `allowed_tools`. Проверьте это разрешение во внешнем диалоге одобрения.
   Иначе оставьте `deny_writes` по умолчанию и используйте воркфлоу только
   для чтения; `inherit` не разрешает запись.
3. Попросите агента запустить его; проверьте сводку одобрения перед принятием.
